# AI의 위험을 부정하려는 이야기가 아닙니다

AI는 잘못된 코드를 만들거나 중요한 보안 조건을 놓칠 수 있습니다. 과도한 권한을 가진 AI 에이전트가 잘못된 명령을 실행하거나, 입력한 시크릿과 운영 정보가 의도하지 않은 방식으로 다뤄질 가능성도 고려해야 합니다.

그렇다고 AI를 사용하지 않고 사람이 직접 작업하면 자동으로 안전해지는 것은 아닙니다. 사람도 설정을 빠뜨리고, 익숙하다는 이유로 검증을 생략하며, 환경변수에 넣었다는 사실만으로 값이 보호된다고 오해할 수 있습니다.

보안은 작업 주체가 사람인지 AI인지로 결정되지 않습니다. 어떤 권한과 정보에 접근할 수 있는지, 결과를 어떻게 검증하고 배포하는지가 더 중요하다고 생각합니다.

## 사람이 관리하던 운영 환경에서도 사고는 발생합니다

과거에 운영 데이터베이스가 침해돼 기존 데이터가 사라지고, 비트코인 지불을 요구하는 내용의 테이블이 남았다는 이야기를 전달받은 적이 있습니다. 같은 환경의 루트(root) 계정 접근이 열려 있었고 제대로 관리되지 않았다는 내용도 들었습니다.

당시 저는 서버 관리 업무를 담당하지 않았고 서버나 운영 환경에 접근할 권한도 없었습니다. 직접 상태와 로그를 확인하지 못했기 때문에 실제 공격 경로가 무엇이었는지, 루트 계정 관리와 데이터베이스 침해가 직접 연결돼 있었는지는 알 수 없습니다.

따라서 이 경험을 특정 설정 때문에 사고가 발생했다는 근거로 사용하지는 않습니다. 다만 사람이 관리하는 환경에서도 높은 권한이 적절히 제한되고 있는지조차 불분명할 수 있고, 사고가 발생한 뒤에도 권한과 기록이 없으면 원인을 확인하기 어렵다는 사실을 체감한 사례로 남아 있습니다.

## APK 안에서 시크릿 문자열을 발견했습니다

다른 작업에서는 React 기반 안드로이드 앱의 APK를 혹시나 하는 마음으로 살펴보다가 시크릿 값이 문자열로 포함된 것을 직접 발견했습니다.

APK는 ZIP 형식을 기반으로 한 애플리케이션 패키지입니다. 내부의 모든 구현이 원본 소스 그대로 보이는 것은 아니지만, 누구나 패키지를 풀어 리소스와 번들을 살펴보거나 문자열을 검색할 수 있습니다. JavaScript 번들이 포함된 React 기반 앱이라면 빌드 과정에서 환경변수 값이 문자열로 치환돼 패키지 안에 남을 수도 있습니다.

환경변수 파일에 값을 적었다는 사실은 서버에서 시크릿을 관리할 때는 의미가 있지만, 그 값이 클라이언트 빌드 결과물에 포함되면 더 이상 비밀이라고 볼 수 없습니다. 사용자의 기기에 배포되는 앱은 사용자가 파일 전체를 가지고 있는 것과 같기 때문입니다.

이 문제는 제 담당 범위가 아니었기 때문에 발견한 값을 사용하거나 임의로 코드를 수정하지 않았습니다. 담당자에게 노출 사실을 전달하는 선에서 멈췄고, 이후 해당 키가 폐기·교체됐는지 또는 앱 구조가 수정됐는지는 확인하지 못했습니다.

## 사람과 AI에 같은 원칙을 적용합니다

저는 AI가 안전하다고 가정하지 않습니다. 사람에게 모든 운영 권한을 한 번에 주지 않는 것처럼 AI에도 최소 권한(least privilege) 원칙을 적용해야 한다고 봅니다.

특히 운영 환경의 계정과 시크릿, 실데이터는 가능한 한 AI에 제공하지 않습니다. 검토에 값이 필요하다면 테스트용 값이나 비식별화한 자료로 대체하고, 운영 환경에 영향을 줄 수 있는 명령과 변경은 별도로 확인합니다.

이 원칙은 AI만을 위한 특별 대우가 아닙니다. 사람의 실수도 막기 위해 사용하던 권한 분리, 시크릿 관리, 변경 승인, 테스트와 로그 확인을 AI 작업에도 그대로 적용하는 것입니다.

## AI는 방어 범위를 넓히는 도구이기도 합니다

AI가 새로운 위험을 만들 수 있다는 이유만으로 보안 검토에서 AI를 제외하는 것은 아쉽다고 생각합니다. 코드와 설정, 배포 산출물을 반복해서 검토하게 하면 사람이 시간과 주의력의 한계로 놓친 취약점 후보를 추가로 발견할 수 있습니다.

AI가 제시한 내용을 바로 확정된 취약점으로 받아들이지는 않습니다. 먼저 요약과 근거가 타당한지 살펴보고 위험도와 변경 비용에 따라 처리 순서를 나눕니다.

- 위험도가 높다면 내용을 한 차례 더 확인한 뒤 우선 보완합니다.
- 위험도가 낮고 안전하게 수정할 수 있다면 보완한 뒤 테스트와 재점검으로 확인합니다.
- 영향은 작지만 기존 구조를 크게 바꿔야 한다면 후순위에 남겨 다른 변경과 함께 검토합니다.

중요한 것은 AI의 판단을 그대로 신뢰하는 것도, AI라는 이유만으로 검토 결과를 버리는 것도 아닙니다. 사람이 위험과 근거를 판단하되 AI를 이용해 확인할 범위와 반복 횟수를 늘리는 방식입니다.

## 공격자가 AI를 사용한다면 방어자도 대비해야 합니다

앞으로 공격자 역시 AI를 이용해 취약점을 찾고 공격 과정을 자동화하려 할 것이라고 생각합니다. 탐색할 대상과 시도할 방법이 늘어나는 상황에서 방어 측이 사람의 수작업 검토에만 의존하면 시간과 주의력, 반복 가능한 검토 범위에서 차이가 벌어질 수 있습니다.

이 관점은 사람을 보안에서 제외해야 한다는 뜻이 아닙니다. 최종적인 권한과 판단 책임은 사람이 가져야 합니다. 다만 사람이 모든 파일과 설정을 매번 빠짐없이 확인할 수 있다는 전제도 현실적이지 않습니다.

AI의 보안 위험을 통제하면서 동시에 방어 도구로 활용하는 편이, AI를 사용하지 않았다는 사실만으로 안전하다고 믿는 것보다 현실적인 대응이라고 봅니다.

## 안전은 작업 방식에서 만들어집니다

사람이 직접 작성한 코드에도 시크릿이 남을 수 있고, 사람이 운영하는 서버에서도 권한 관리가 빠질 수 있습니다. AI가 만든 결과물에도 같은 문제가 생길 수 있습니다.

그래서 안전을 사람과 AI 가운데 하나를 선택하는 문제로 보지 않습니다. 운영 정보는 처음부터 분리하고, 필요한 권한만 제공하며, 결과물을 여러 방식으로 검토하고, 위험도에 따라 보완 순서를 정해야 합니다.

AI가 보안상 위험할 수 있다는 말은 맞습니다. 그러나 그 말이 수작업은 안전하다는 결론으로 이어지지는 않습니다. 중요한 것은 누가 만들었는지가 아니라, 어떤 원칙으로 제한하고 확인했는지입니다.
