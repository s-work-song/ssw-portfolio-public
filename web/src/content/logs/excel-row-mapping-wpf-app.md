# 반복적인 주소 조회와 엑셀 입력 작업이었습니다

간단한 부업으로 토지 주소와 소유주 정보가 비어 있는 행이 담긴 엑셀 파일을 받아 작업한 적이 있습니다. 각 주소를 기준으로 정부24에서 토지대장 정보를 조회한 뒤, 확인한 정보를 다시 원본 엑셀의 해당 행에 채워 넣는 반복 작업이었습니다.

정확한 시작일은 기억나지 않지만 남아 있는 백업 기록을 기준으로 보면 2024년 초부터 2025년 말까지 약 2년 동안 제작·보완하며 실제 작업에 사용한 것으로 보입니다.

주소를 한 건씩 조회하고 결과를 복사해 엑셀에 붙여 넣는 방식으로는 건당 단가를 시간으로 환산했을 때 거의 최저시급에 가까웠습니다. 프로그래머의 역할은 이런 반복을 찾아 도구와 구조로 줄이는 것이라고 이전부터 생각했고, 실제 작업에 사용할 유틸리티를 직접 만들기 시작했습니다.

## 신청은 반자동화하고 결과 매핑은 자동화했습니다

정부24의 작업 흐름은 신청과 결과 수집의 두 단계로 나뉘었습니다.

신청 단계는 최종 제출까지 포함해 전자동으로 동작하도록 한 차례 시험해 봤고, 기술적으로 가능하다는 것도 확인했습니다. 요청 사이에 딜레이를 두는 방식으로 구성했지만, 당시 사이트 이용약관과 자동화 허용 범위를 정확히 확인하지 못한 상태였습니다. 딜레이를 준다는 사실만으로 자동 제출이 약관상 허용된다고 볼 수는 없었고, 이용상 불이익이 생길 가능성을 피하기 위해 보수적으로 접근했습니다.

그래서 실제 작업 흐름에서는 최종 신청 버튼을 자동으로 누르는 기능을 제외했습니다. 스크립트가 반복 입력값을 채우고, 사람이 내용을 확인한 뒤 직접 신청 버튼을 누르는 반자동 방식으로 사용했습니다. 최종 제출을 수동으로 남긴 것은 사이트 약관과 자동화 범위가 불명확한 상황에서 위험을 줄이기 위한 선택이었습니다.

결과 수집 방식은 외부 사이트의 변화에 맞춰 바뀌었습니다. 처음에는 신청 내역을 JSON으로 한 번에 받아 처리했습니다. 이후 정부24 사이트가 개편되면서 필요한 값을 같은 방식으로 조회하기 어려워졌고, 결과를 MHTML 파일로 내려받은 뒤 필요한 내용을 파싱하는 방식으로 변경했습니다.

파싱한 결과는 주소와 지번을 정부24 공공데이터 형식에 맞춰 정규화한 뒤 원본 엑셀의 행과 비교했습니다. 잘못된 소유주 정보를 다른 행에 연결하는 것보다 일부를 수작업으로 남기는 편이 안전하다고 판단했습니다. 따라서 일치 여부를 보수적으로 판정하고 애매한 항목은 직접 확인해 처리했습니다.

## WinForms 프로토타입을 WPF MVVM으로 옮겼습니다

이 작업으로 Windows 데스크톱 앱 개발을 처음 접했습니다. 시작할 때는 WinForms와 WPF 모두 사용해 본 적이 없었습니다.

필요한 기능을 만들기 위해 WinForms와 WPF를 알아보는 과정에서, WPF에서는 MVVM 패턴을 함께 사용하는 것이 일반적이고 이를 익히는 데 러닝커브가 있다는 점을 알게 됐습니다.

MVVM 자체가 완전히 새로운 개념은 아니었습니다. 과거 Android Java 환경의 작은 개인 프로젝트에서 시험해 본 적이 있었고, Vue.js 환경에서도 MVVM과 유사한 데이터 바인딩과 역할 분리를 접했습니다. 다만 WPF에서 구체적으로 적용하는 방식은 알지 못했습니다.

우선 필요한 기능을 빠르게 사용하기 위해 WinForms로 가벼운 프로토타입을 만들었습니다. 이후 실제 작업에 사용하면서 WPF와 그 안에서의 MVVM 적용 방식을 천천히 학습했고, 기존 기능을 WPF 구조로 마이그레이션했습니다.

처음부터 완성된 구조를 설계한 것이 아니라 당장 필요한 기능을 먼저 만들고, 새로운 방식을 학습하면서 실사용 도구를 단계적으로 옮긴 과정이었습니다.

## 실제 요구사항이 여러 기술을 학습할 기회가 됐습니다

자동화하면 생산성이 높아진다는 사실이나 전체 작업 흐름을 설계하는 것이 중요하다는 점은 이전부터 프로그래머의 역할로 인식하고 있었습니다. 이 작업에서 더 크게 남은 것은 실제 필요에 따라 여러 기술을 직접 시험하고 사용해 볼 수 있었다는 점입니다.

엑셀과 문서 데이터를 처리하는 과정에서 다음 기술을 실제 기능에 활용했습니다.

- NPOI를 사용해 엑셀을 다루고, 대용량 파일에 대비해 ExcelDataReader로 읽기 성능 개선
- Newtonsoft.Json 외에 System.Text.Json을 사용하며 `ref struct` 기반 처리 방식 학습
- 처음 접한 MHTML 형식을 처리하고 Html Agility Pack으로 HTML 파싱
- HTML의 `charset`을 확인하기 위해 문서 앞부분을 직접 읽어 인코딩 판별
- Win32 User32 API를 활용한 마우스 이동과 클릭 처리
- 반자동 입력을 단축키처럼 사용하기 위한 SendInput 활용

개인 학습용 예제를 따로 만드는 방식과 달리, 실제로 사용해야 하는 하나의 도구 안에서 파일 크기와 인코딩, 외부 사이트 변경, 입력 보조와 데이터 검수까지 이어지는 문제를 함께 경험할 수 있었습니다.

## 처리 효율이 약 5배 높아졌습니다

반자동 조회와 자동 매핑을 적용한 뒤에는 체감 처리 효율이 약 5배 높아졌습니다. 건당 단가를 작업 시간으로 환산했을 때 거의 최저시급에 가까웠던 일이 시간당 약 5만 원 수준의 작업으로 바뀌었습니다. 이는 당시 개인 작업량과 단가를 기준으로 한 체감치이며 모든 환경에서 같은 결과가 나온다는 의미는 아닙니다.

작업이 몰릴 때는 다른 작업자가 조회와 파일 저장을 담당하고, 저는 전달받은 파일을 자동 매핑한 뒤 최종 결과를 검수하는 방식으로 역할을 나눌 수도 있었습니다. 개인용 유틸리티를 넘어 반복 작업의 일부를 분리해 외주로 맡길 수 있는 파이프라인이 만들어진 셈입니다.

## 지금 다시 만든다면 작업 방식부터 달라집니다

제가 이 작업을 시작했을 때는 지금처럼 코딩 에이전트에게 구현을 맡기는 개념 자체가 없었습니다. GPT 챗봇도 현재보다 환각이 잦다고 느끼던 시기라 유료 구독 없이 무료 계정으로 생소한 기술을 알아보는 학습 보조 정도로만 사용했습니다. 구조 결정과 구현, 검증은 직접 진행했습니다.

지금 같은 기능을 다시 만든다면 정확한 소요 시간을 단정할 수는 없지만 기본 형태는 시간 단위가 아니라 분 단위로 만들 수도 있을 것 같습니다. 라이브러리를 조사하고 반복 코드를 작성하는 속도는 당시와 비교하기 어려울 정도로 빨라졌습니다.

다만 주소 정규화와 매핑 결과처럼 잘못 연결됐을 때 문제가 생기는 최종 결과물은 여전히 사람이 보수적으로 확인해야 한다고 봅니다. 구현 시간이 크게 줄어들더라도 무엇을 자동화할지 정하고, 애매한 결과를 분리하며, 최종 데이터의 정확성을 책임지는 판단까지 자동으로 해결되는 것은 아닙니다.

이 앱은 반복 작업을 줄인 도구이면서, 실제 문제를 해결하는 과정에서 Windows 앱과 데이터 처리 생태계를 넓게 학습한 손 코딩 프로젝트로 남아 있습니다.
