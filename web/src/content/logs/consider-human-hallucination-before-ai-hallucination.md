# 어느 날 구조체의 접근 제한자를 질문받았습니다

어느 날 지인에게 구조체의 기본 접근 제한자가 무엇인지 질문받았습니다. 저는 하나의 답을 바로 말하기보다 언어마다 규칙이 다를 것이라고 답했습니다.

그 뒤 지인이 질문의 배경을 들려줬습니다. 지인은 Unity·C# 개발자 포지션에 지원했고, 면접에서 구조체의 기본 접근 제한자가 무엇인지 질문받았다고 했습니다. 질문에는 어떤 언어인지, 구조체 타입 자체와 내부 멤버 가운데 무엇을 뜻하는지 별도로 명시되지 않았다고 합니다.

지인이 `private`이라고 답하자 면접관은 틀렸다며 정답은 `public`이라고 말했다고 합니다. 지인이 전한 기억으로는 면접관이 자신의 답을 매우 확신하는 태도였다고 합니다. 이후 그 면접관이 C++ 개발자였다는 이야기도 들었습니다.

저는 면접에 직접 참여하지 않았습니다. 정확한 질문 문장과 앞뒤 대화, 면접관의 의도를 확인할 수 없기 때문에 이 내용은 어디까지나 지인에게 전달받은 면접 후기라는 한계가 있습니다. 면접관이 실제로 C#을 몰랐거나 의도적으로 잘못 평가했다고 단정하지도 않습니다.

## 질문에는 언어와 대상이 필요합니다

이 질문은 언어와 대상을 지정하지 않으면 하나의 답을 정하기 어렵습니다.

C#에서는 구조체 내부 멤버의 접근 제한자를 생략하면 기본적으로 `private`입니다. 네임스페이스에 선언한 최상위 구조체 타입 자체는 기본적으로 `internal`이고, 다른 타입 안에 선언한 중첩 구조체 타입은 기본적으로 `private`입니다. 이 기준은 [Microsoft의 C# 접근성 문서](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/keywords/accessibility-levels)와 [중첩 타입 문서](https://learn.microsoft.com/en-us/dotnet/csharp/programming-guide/classes-and-structs/nested-types)에서 확인할 수 있습니다.

```csharp
struct Sample
{
    int value; // 구조체 멤버이므로 기본 private
}

class Container
{
    struct NestedSample { } // 중첩 타입이므로 기본 private
}
```

위 코드에서 최상위 타입인 `Sample` 자체의 기본 접근성은 `internal`입니다. 지인이 면접에서 `private`이라고 답한 것은 구조체 타입 자체가 아니라 C# 구조체의 내부 멤버를 묻는 것으로 해석한 답입니다.

반면 C++에서는 `struct`로 선언한 타입의 멤버가 기본적으로 `public`입니다. 이 내용은 [C++ 표준 초안의 멤버 접근 제어 항목](https://eel.is/c%2B%2Bdraft/class.access.general)에서도 확인할 수 있습니다.

```cpp
struct Sample
{
    int value; // C++에서는 기본 public
};
```

따라서 전달받은 내용 그대로라면 면접관의 답은 C++ 구조체 멤버를 기준으로는 맞지만, Unity·C# 포지션의 구조체 멤버를 묻는 답으로는 맞지 않습니다. 동시에 질문 자체도 어떤 언어의 무엇을 묻는지 충분히 한정하지 않았습니다.

## 확신과 직위는 정답의 근거가 아닙니다

누구나 기억을 잘못 떠올리거나 서로 다른 언어의 규칙을 섞을 수 있습니다. 사람의 기억은 영원하거나 완전하지 않으며, 이것은 저 자신에게도 똑같이 적용된다고 생각합니다.

문제는 기억이 틀릴 수 있다는 사실보다 틀릴 가능성을 인정하지 않은 채 검증을 생략하는 태도입니다. 특히 평가 권한을 가진 사람이 자신의 기억을 정답으로 확정하면, 맞는 답을 한 지원자가 오히려 틀린 것으로 평가될 수 있습니다.

AI의 환각은 많은 사람이 경계합니다. AI가 그럴듯한 설명으로 틀린 답을 제시할 수 있다는 사실은 분명히 확인해야 합니다. 하지만 사람 역시 같은 방식으로 잘못된 내용을 확신할 수 있고, 그 사람이 면접관이나 의사결정권자라면 오류가 평가 기준이나 조직의 규칙이 될 수도 있습니다.

사람의 환각이 언제나 AI보다 더 자주 발생한다고 주장하려는 것은 아닙니다. 다만 권한과 자신감이 더해진 사람의 오류는 다른 사람의 평가와 선택에 직접 영향을 줄 수 있다는 점에서 더 큰 문제가 될 수 있다고 봅니다.

## 잘못된 정의가 지역적인 정답이 되기도 합니다

이 사례는 이전에 정리한 [RESTful과 RPC를 같은 의미로 부르지 말아야 합니다](../do-not-call-restful-and-rpc-the-same/)라는 기록과도 연결됩니다.

잘못된 정의라도 결정권을 가진 사람이 확신하면 특정 조직 안에서는 그것이 사실상의 정답이 될 수 있습니다. 다른 의견을 가진 소수는 매번 충돌하기보다 협업을 위해 그 기준에 순응하기도 합니다.

단기적인 협업에서는 소수가 지역적인 규칙에 맞추는 편이 비용이 적을 수 있습니다. 그러나 그 표현과 정의가 외부 사람이나 새로운 구성원, 국제적인 문서와 AI 도구를 계속 만나야 한다면 잘못된 기준은 반복해서 혼란을 만듭니다.

면접도 마찬가지입니다. 평가자가 만든 지역적인 정답이 언어의 실제 규칙과 다르면, 지원자의 지식보다 평가자의 기억에 맞는 답을 고르는 시험이 됩니다.

## 기억보다 작은 검증을 먼저 믿습니다

제가 알고 있는 내용도 시간이 지나면 틀릴 수 있습니다. 그래서 간단하게 확인할 수 있는 문제라면 짧은 코드를 직접 컴파일해 결과를 확인하는 편입니다. 그 과정에서 공식 문서와 언어 명세도 함께 살펴봅니다.

최근에는 AI에게 최소한의 재현 코드를 만들고 빠른 테스트를 실행하도록 요청하기도 합니다. 그렇다고 AI의 설명을 새로운 정답으로 받아들이지는 않습니다. 실제 컴파일 결과와 공식 문서를 확인하는 데 드는 비용을 줄이는 도구로 사용합니다.

```text
기억한 답
  → 최소 코드로 재현
  → 컴파일 결과 확인
  → 공식 문서와 대조
```

이 과정은 상대방이 틀렸다는 사실을 증명하기 위해서만 필요한 것이 아닙니다. 제 기억이 잘못됐을 가능성도 같은 기준으로 확인하기 위한 절차입니다.

## 질문의 수준은 난이도만으로 정해지지 않습니다

기본 문법을 묻는 질문 자체가 항상 나쁘다고 생각하지는 않습니다. 다만 정답을 평가하려면 질문자가 언어와 대상을 정확히 한정하고, 자신의 답이 맞는지도 확인할 수 있어야 합니다.

어려운 질문을 했다는 사실이 면접의 수준을 높이지 않습니다. 모호한 질문에 하나의 답만 정해 두고 다른 해석을 오답으로 처리하면 지원자의 역량보다 면접관의 전제를 맞히는 능력을 평가하게 됩니다.

AI에게는 출처와 재현을 요구하면서 사람의 말은 직위나 자신감만으로 믿는 태도도 일관되지 않습니다. AI와 사람 모두 틀릴 수 있다면 같은 검증 원칙을 적용해야 합니다.

AI의 환각을 경계하기 전에 사람의 기억과 확신도 먼저 돌아봐야 합니다. 정답을 결정하는 것은 말하는 사람의 자신감이 아니라 명확한 문맥과 재현 가능한 결과, 확인할 수 있는 근거라고 생각합니다.
