# 처음 접한 코딩은 나와 맞지 않는다고 생각했습니다

코드를 처음 접한 것은 컴퓨터계열 고등학교에서 C언어를 배웠을 때였습니다. 당시 교과 과정에서는 C언어의 기본 문법과 조건문·반복문을 거쳐 포인터라는 개념이 있다는 정도까지 배운 것으로 기억합니다.

별도의 완성도 있는 프로그램을 만들었던 기억은 없고, 이 경험을 C언어 개발 역량으로 내세우려는 것은 아닙니다. 다만 처음 프로그래밍을 접했을 때 어떤 인상을 받았는지를 설명하는 출발점입니다.

절차지향 방식으로 처음 코드를 접하면서, 기능과 실행 환경이 늘어날 때마다 모든 경우를 직접 분기하고 처리해야 한다고 받아들였습니다. Windows, Linux, 모바일처럼 환경이 달라질 때마다 별도 조건과 흐름을 계속 추가해야 한다고 생각하니 엄청난 반복 작업처럼 느껴졌습니다.

물론 C언어나 절차지향 프로그래밍이 반드시 모든 환경을 거대한 조건문으로 처리해야 한다는 뜻은 아닙니다. 당시 학생이었던 제가 그렇게 이해했다는 이야기입니다.

## 관심의 중심은 하드웨어였습니다

당시 관심의 중심은 코딩보다 컴퓨터 하드웨어였습니다. CPU 오버클럭과 벤치마킹, SSD RAID 0과 그래픽 카드 SLI 구성을 직접 시험하면서 여러 장치를 조합해 컴퓨터 자원의 성능을 끌어내는 일에 흥미를 느꼈습니다.

코드는 아직 관심의 대상이라기보다 복잡한 반복 작업처럼 보였습니다.

## 문제를 직접 처리할 수 있는 위치로

개발을 진지하게 생각하기 시작한 것은 2014년 시스템 운영 업무를 마친 뒤였습니다.

업무 중 문제가 생겼을 때 해결 방법보다 누가 담당해야 하는지를 정하는 과정이 길어지는 환경을 경험했습니다. 운영 담당자로서는 문제를 확인하고 전달할 수는 있어도 코드를 직접 수정할 수 없었습니다.

담당 범위를 조율하고 다른 사람의 처리를 기다리기보다, 문제를 해결할 수 있는 위치에서 원인과 코드를 직접 확인해 처리하고 싶었습니다. 그 답답함이 개발을 선택하게 된 계기였습니다.

바로 개발을 시작한 것은 아니었습니다. 군 복무를 마치고 나면 개발을 배워야겠다고 방향을 정했고, 전역한 2018년에 개발자 교육 과정으로 실제 첫걸음을 옮겼습니다.

## 객체지향이 코딩에 대한 인상을 바꿨습니다

학원을 정하기 전에 개발 분야를 알아보는 과정에서 객체지향 프로그래밍(OOP)이라는 개념을 먼저 접했습니다.

기능과 책임을 객체 단위로 나누고, 공통된 사용 방식과 환경별 구현을 분리할 수 있다는 설명은 고등학교 때 코딩에 가졌던 인상을 크게 바꿨습니다. 모든 상황을 하나의 흐름 안에서 직접 처리하는 것이 아니라, 역할별로 나눈 구조를 조합해 사용할 수 있다는 점이 개발에 느꼈던 심리적인 장벽을 낮춰줬습니다.

처음 배우기에 비교적 보편적이고 자료가 많다고 판단한 Java를 언어로 선택했습니다. 국내 개발 업계에서 취업 경로가 넓고 무난하다고 본 Spring 기반 웹 개발자 과정도 함께 선택했습니다.

## 교육 과정 밖에서 객체지향을 다시 공부했습니다

Java·Spring 교육 과정에 들어갔지만 기대했던 것처럼 객체지향의 원리와 설계 이유를 깊게 설명하는 수업은 아니었습니다. 체감상 고등학교 때의 프로그래밍 수업과 크게 다르지 않았고, 개념을 이해하기보다 문법과 사용법을 암기하고 예제를 따라 한 뒤 나머지는 과제로 해결하는 방식에 가까웠습니다.

그래서 교육 과정과 별개로 객체지향 개념을 혼자 다시 공부했습니다. 단순히 클래스를 만드는 문법을 넘어 객체가 어떤 책임을 가져야 하는지 찾아보다가 SOLID 원칙과 디자인 패턴까지 접하게 됐습니다.

가장 먼저 와닿은 것은 단일 책임 원칙(SRP)이었습니다.

당시에는 정식 개념을 알지 못한 채 ‘어떻게 나눠야 객체지향다운 구조가 될까’를 고민하며 하나의 긴 흐름을 기능별 함수로 나누고, 비슷한 기능을 담당하는 함수들을 별도의 클래스로 묶어 보고 있었습니다.

그러다 제가 막연하게 시도하던 방향에 단일 책임 원칙이라는 이름과 정형화된 설명이 있다는 사실을 알게 됐습니다. 혼자 느끼던 문제를 이미 다른 개발자들이 개념과 규칙으로 정리해 두었다는 점에서 머리가 트이는 듯한 느낌을 받았습니다. 그 경험을 계기로 다른 SOLID 원칙과 디자인 패턴도 곧바로 찾아보기 시작했습니다.

## 배운 원칙과 실무 사이의 간극

교육 이후에는 Java 기반 웹과 Android 개발 업무를 경험했습니다. 독학하며 익힌 객체지향 원칙과 실제 프로젝트의 코드 구조 사이에는 상당한 차이가 있었습니다.

기능과 책임이 뒤섞인 구조를 개선하고 싶었지만, 설계 관점에 대한 공통된 기준을 만들거나 충분히 논의하기도 어려웠습니다. 처음에는 제가 이해한 원칙을 적용하려 했지만 개인의 판단만으로 기존 구조와 협업 방식을 바꾸는 데는 한계가 있었습니다.

결국 실무에서는 현재 구조와 팀의 방식에 제가 맞추는 쪽을 선택했습니다. 객체지향에 대한 관심을 버린 것은 아니었지만, 업무 안에서 원하는 만큼 실험하기는 어렵다는 사실을 받아들인 시기였습니다.

## Unity와 C#에서 다시 시작한 실험

게임은 언젠가 직접 만들어 보고 싶다고 오래전부터 생각하고 있었습니다. Java 개발을 시작한 지 약 3년이 지난 뒤, 다른 사람의 구조에 맞추는 것이 아니라 처음부터 직접 구조를 정하고 실험할 수 있는 개인 게임 개발을 시작하기로 결심했습니다.

비교적 가볍게 접근할 수 있다고 판단한 Unity로 시작했습니다. C#에도 이전부터 어느 정도 관심이 있었습니다. Unreal Engine의 존재도 알고 있었지만, 당시에는 개발과 실행에 더 높은 컴퓨팅 환경이 필요하다고 생각해 처음 접근하기에는 부담이 있다고 판단했습니다.

Unity를 사용하면서 C#을 본격적으로 접했습니다. 당시 익숙했던 Java와 비교하면 C#에는 낯선 개념이 많았고, 그중 가장 크게 다가온 것은 구조체였습니다.

처음에는 클래스와 구조체의 차이가 혼란스러웠지만 값 형식이라는 특성을 이해한 뒤에는 구조체를 활용한 여러 실험을 직접 해 보기 시작했습니다. 값 복사가 실제로 어떻게 일어나는지, 참조 형식과 비교했을 때 메모리 할당 방식이 어떻게 달라지는지 살펴봤습니다. `ref`, `in`, `out` 키워드가 데이터를 전달하는 방식과 실제 동작도 작은 코드를 작성해 확인했습니다.

이 과정에서 구조체를 사용한다고 항상 성능이 좋아지는 것은 아니라는 점도 알게 됐습니다. 읽기 전용 문맥이나 멤버 접근 방식에 따라 방어적 복사가 발생하면 오히려 성능이 떨어질 수 있었고, 이를 줄이거나 변경 의도를 명확히 하는 읽기 전용 구조체와 읽기 전용 멤버의 유용성도 이해하게 됐습니다.

Unity 자체도 제공되는 기능을 그대로 사용하는 데서 끝나지 않았습니다. 기본 기능과 Inspector만으로는 원하는 작업 흐름을 만들기 불편한 부분이 있었고, 필요한 기능을 직접 구성하기 위해 Custom Inspector를 만들어 볼까 고민하면서 Unity 에디터와 내부 동작을 조금씩 깊게 살펴보기 시작했습니다.

게임 제작을 목적으로 시작했지만 관심은 점차 엔진과 언어가 어떻게 동작하는지, 메모리와 데이터가 어떤 비용으로 처리되는지를 연구하는 쪽으로 확장됐습니다.

## 코딩은 관심의 대상보다 수단에 가깝습니다

컴퓨터 자원을 구성하고 활용하는 일에 대한 관심은 학생 때부터 지금까지 크게 달라지지 않았습니다. 하드웨어만 다루던 시기에는 코딩이 저와 맞지 않는 반복 작업처럼 보였습니다.

객체지향은 복잡성을 역할과 책임으로 나눌 수 있다는 관점을 보여줬고, 개발 실무는 문제를 직접 처리할 수 있는 수단을 줬습니다. Unity와 C#을 통한 개인 연구는 하드웨어에서 시작한 관심을 메모리와 소프트웨어 구조까지 연결했습니다.

저는 코딩 자체를 목적으로 개발을 시작한 것이 아닙니다. 다른 사람의 처리를 기다리기보다 문제를 직접 해결하고, 컴퓨터라는 기계와 그 안의 자원을 더 깊게 구성하고 활용하기 위해 개발을 선택했습니다. 지금도 코드는 그 목적을 실현하기 위한 수단에 가깝습니다.
