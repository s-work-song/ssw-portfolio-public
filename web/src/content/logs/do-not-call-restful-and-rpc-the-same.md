# `GET`과 `POST`만 안전하다는 규칙

과거 한 업무 환경에서 `GET`과 `POST` 이외의 HTTP 메서드는 위험하므로 차단해야 한다는 설명을 들었습니다. 실제 환경도 그 기준에 맞춰 다른 메서드를 사용할 수 없게 구성돼 있었습니다.

자원의 생성·수정·삭제 같은 행위는 모두 `POST`로 요청하고, `create`, `update`, `delete`와 같은 동사를 경로의 접두사나 접미사에 넣어 구분했습니다. 그러면서 이 방식을 RESTful이라고 불렀습니다.

당시 API는 기능적으로 특별한 문제 없이 동작했습니다. `POST`만으로도 필요한 처리를 구현할 수 있었고, 호출하는 쪽에서도 정해진 경로를 사용하면 됐습니다.

제가 다르게 생각한 부분은 동작 여부가 아니라 **그 구조를 설명하는 명칭과 근거**였습니다.

## REST는 메서드 이름만으로 결정되지 않습니다

REST는 하나의 API 명세서가 아니라 분산 하이퍼미디어 시스템을 위한 아키텍처 스타일입니다. Roy Fielding이 정리한 REST의 핵심에는 클라이언트와 서버의 분리, 무상태성, 캐시, 계층화된 시스템과 함께 일관된 인터페이스(uniform interface)가 포함됩니다.

따라서 `GET`, `POST`, `PUT`, `PATCH`, `DELETE` 중 여러 메서드를 사용했다는 사실만으로 어떤 API가 완전한 REST 구조가 되는 것은 아닙니다.

다만 RESTful한 HTTP API에서 메서드는 단순한 전송 수단도 아닙니다. 자원을 식별하고, 자원에 어떤 의미의 요청을 보내는지 표준화된 인터페이스로 표현하는 요소입니다. Fielding의 REST 설명에서도 자기 서술적인 메시지를 위해 표준 메서드와 미디어 타입이 의미를 나타낸다고 설명합니다.

예를 들어 다음 두 형태는 호출 의도를 표현하는 방식이 다릅니다.

```http
POST /users/create
POST /users/update
POST /users/delete
```

```http
POST   /users
PUT    /users/42
DELETE /users/42
```

첫 번째 형태는 경로에 실행할 동사를 넣어 원격 동작을 호출하는 RPC 성격이 강합니다. 두 번째 형태는 `/users`라는 자원을 중심에 두고 HTTP 메서드의 의미로 행위를 구분합니다.

RPC 형태가 REST보다 열등하거나 잘못된 것은 아닙니다. 특정 절차나 명령을 원격에서 실행하는 것이 목적이라면 RPC가 더 자연스러울 수 있습니다. 문제는 RPC 성격의 구조를 선택했다는 데 있지 않습니다. 그 구조를 RESTful의 정의라고 설명한 데 있습니다.

## 메서드는 죄가 없습니다

`DELETE`라는 이름은 무언가를 지우기 때문에 위험해 보일 수 있습니다. 하지만 HTTP 메서드의 이름이 서버에 없는 권한이나 기능을 만들어 내지는 않습니다.

서버에 삭제 처리 코드가 없거나 요청자에게 권한이 없다면 `DELETE` 요청만으로 자원이 삭제되지 않습니다. 반대로 다음과 같은 `POST` 요청에도 계정 삭제나 데이터 초기화처럼 큰 영향을 주는 로직을 연결할 수 있습니다.

```http
POST /accounts/delete
POST /database/reset
```

HTTP 표준은 메서드마다 의미와 안전성(safety), 멱등성(idempotency)을 구분합니다. 이때 안전한 메서드라는 표현은 보안 취약점이 없다는 뜻이 아니라, 클라이언트가 서버 상태 변경을 요청하지 않는 읽기 중심의 의미를 가리킵니다. `POST` 역시 표준에서 안전하지 않고 멱등적이지 않은 메서드로 분류됩니다.

실제 보안은 요청자의 인증과 권한, 대상 자원에 대한 접근 제어, 입력 검증, 요청 위조 방어와 서버에 연결된 처리 로직으로 결정됩니다. `POST`라는 이름을 사용했다고 안전해지는 것도 아니고, `PUT`이나 `DELETE`라는 이름을 사용했다고 위험해지는 것도 아닙니다.

물론 서비스에서 사용하지 않는 메서드를 허용 목록에서 제외하는 것은 방어 계층의 하나가 될 수 있습니다. 서버가 지원하지 않는 기능과 불필요한 공격 표면을 줄이는 구성 자체는 이상하지 않습니다. 그러나 필요한 `PUT`, `PATCH`, `DELETE`까지 이름만으로 위험하다고 판단하고 모든 행위를 `POST` 안으로 옮기는 것은 메서드 차단과는 다른 문제입니다.

## 순응하는 것과 정의에 동의하는 것은 다릅니다

저는 당시 이 차이를 설명하려고 했습니다. 다른 HTTP 메서드 자체가 위험한 것은 아니며, 인터넷에서 그런 내용을 접했다면 잘못 전달된 정보일 수 있다고 이야기했습니다. 경로의 동사와 `POST`로 원격 동작을 구분하는 방식에는 RPC라는 별도의 명칭이 있다는 점도 전달하려 했습니다.

설득을 오래 이어가지는 않았습니다.

이미 다수가 같은 규칙을 사용하고 있는 환경에서 소수가 계속 이견을 제기하면, 개념을 바로잡아서 얻는 이점보다 당장의 협업 비용이 더 커질 수 있습니다. 그 환경에서는 그것이 맞는 규칙으로 통용됐고, 저는 기존 방식에 맞춰 일하기로 했습니다.

이는 구현 규칙에 순응한 것이지, 내부에서 사용하는 표현까지 외부의 정의와 같다고 받아들인 것은 아니었습니다.

조직이 기존 시스템이나 호환성 때문에 `POST` 중심의 RPC 구조를 유지할 수는 있습니다. 그 방식을 RPC라고 정확하게 명시하고 내부 규칙을 문서화한다면, 참여자는 같은 전제에서 작업할 수 있습니다. 표준과 다른 선택을 하는 것과 표준의 의미를 바꿔 부르는 것은 구분해야 합니다.

## 구성원은 계속 바뀝니다

현재 구성원 모두가 내부 용어를 이해하고 있다면 잘못된 정의도 당장은 별문제 없이 작동할 수 있습니다. 단기적인 협업만 보면 새로운 사람이 기존 다수의 표현에 순응하는 것이 빠를 수도 있습니다.

하지만 프로젝트와 조직의 구성원은 계속 바뀝니다. 신규 개발자와 외부 협력자, 유지보수를 맡은 사람이 들어올 때마다 내부에서만 사용하는 의미를 다시 설명해야 합니다.

국제적으로 통용되는 정의와 공개 표준은 모든 조직이 반드시 같은 구현을 선택하게 만들기 위한 규칙만은 아닙니다. 서로 다른 배경을 가진 사람들이 같은 용어를 들었을 때 비슷한 구조와 의미를 예상할 수 있게 하는 공통 언어이기도 합니다.

RESTful이라고 적힌 문서를 읽은 사람이 자원과 HTTP 메서드의 의미를 활용한 인터페이스를 예상하는 것은 자연스럽습니다. 실제 구조가 실행 동사를 경로에 넣은 RPC 형태라면, 문서의 이름과 구현이 서로 다른 정보를 주게 됩니다.

## 이제는 AI도 문서와 코드를 읽습니다

당시에는 ChatGPT가 대중에게 공개되기 훨씬 전이었으므로 이 경험과 AI는 관계가 없었습니다. AI의 환각과 연결해 생각하게 된 것은 이후 실제 개발에 AI를 활용하면서부터입니다.

AI는 공개된 문서와 널리 통용되는 용어를 바탕으로 코드의 의도를 해석합니다. 프로젝트가 통용되는 정의와 다른 의미로 용어를 사용하면서 그 차이를 명확히 기록하지 않으면, 사람뿐 아니라 AI에도 서로 충돌하는 맥락을 제공하게 됩니다. 이는 잘못된 추론이나 환각이 발생할 가능성을 높일 수 있습니다.

그렇다고 사람은 정확하고 AI만 환각한다는 의미도 아닙니다. 출처를 확인하지 않은 정보를 그럴듯한 설명과 함께 확신하는 일은 사람에게도 생길 수 있습니다. 다만 이 주제는 AI를 활용하며 갖게 된 관점으로 별도의 글에서 더 자세히 다루려고 합니다.

이 글에서 말하고 싶은 것은 더 단순합니다.

## 다르게 선택할 수 있지만 다르게 불러서는 안 됩니다

개인적으로는 자원을 중심으로 상태를 조회하거나 변경하는 API를 RESTful하게 구성하려고 합니다. 특정 절차나 명령을 원격에서 실행하는 것이 목적이라면 RPC 형태를 선택할 수 있습니다. 어느 방식이 더 우월해서가 아니라 표현하려는 대상과 요구사항에 더 적합한 방식을 선택하기 위해서입니다.

협업할 때는 개인의 선호보다 해당 프로젝트와 조직의 기존 규칙을 따릅니다. 기존 구조를 당장 바꾸는 비용이 더 클 수 있다는 것도 알고 있습니다.

그러나 내부 규칙을 따르는 것과 그 방식을 외부의 기술적 정의와 동일시하는 것은 별개입니다.

비표준적인 선택도 명확한 이유가 있고 문서로 설명할 수 있다면 사용할 수 있습니다. 다만 이미 통용되는 이름을 다른 의미로 바꿔 부르면, 현재의 구성원은 적응할 수 있어도 미래의 구성원과 외부 도구는 잘못된 출발점에서 시스템을 이해하게 됩니다.

그래서 RESTful과 RPC를 같은 방식으로 부르지 말아야 한다고 생각합니다.
